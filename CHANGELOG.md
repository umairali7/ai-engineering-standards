# Changelog

All notable changes to the AI Engineering Standards (AIES) project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html) for the standard as a whole (see [GOVERNANCE.md §6](GOVERNANCE.md#6-releases)). Individual documents carry their own version and status per the [Shared conventions](Shared/README.md).

- **Complete ADR-0012 qualification-integrity protocol**: human raters now have immutable registry records covering durable identity, competency/risk scope, current qualification, current calibration, anchor-library version, and registry authority. Evidence Package v5 admits formal qualification evidence only from verified conflict-free humans, enforces 20% independent double-rating at RT1 — Minimal / RT2 — Moderate and 100% at RT3 — Significant / RT4 — Critical, requires at least 80% adjacent agreement, and blocks unresolved material divergences. - **Evidence Package v5 resolved-item protocol**: rating records are retained as immutable observations while qualification statistics consume at most one resolved score per response evidence item. Multiple human ratings cannot increase statistical `n` or narrow confidence as independent samples; adjacent ratings resolve conservatively to the lower demonstrated anchor, and a two-point-or-greater divergence remains excluded until an immutable, named-human disposition records its score and rationale. Review packages retain every human and model rater rather than overwriting the first rater of each kind. Legacy Evidence Package v4 artifacts remain readable under their original meaning.

The authoritative backlog now includes a full “killer demo” rebuild covering the complete subject-neutral AIES story and linked decision-product bundle.

- **Non-blocking automated Engineering Evaluation**: complete automated scoring now closes the engineering-evaluation workflow and produces a schema-versioned `engineering-evaluation.json` alongside Markdown, HTML, JSON, and ECM artifacts. Human evaluation adds assurance but is not required to finish or report an engineering evaluation; formal qualification/grant readiness remains a separate ADR-0012 human-governed decision.

- **Detailed live and durable run progress**: `qualify`, resume, `review`, and `score` show progress implicitly. Long-running response collection, journey execution, judge review, score admission, aggregation, and report generation emit stage, completed/total, percentage, per-stage and total elapsed time, throughput, ETA, failures, and the current human-readable scenario family/task objective with its ordinal. Judge activity identifies scoring across EV1 — Correctness through EV6 — Traceability. Parallel runs report the dynamic active task set and effective capacity for any configured `--parallel N`; no worker count is hard-coded. Interactive CLIs update in place; redirected logs emit throttled 5% checkpoints. Every run persists its current operational state in `progress.json`; `aies runs progress <run-id>` is an optional second-terminal observer. Collection resumes and journeys persist an explicit partial/failed terminal state while preserving successful work.

A repository-wide Document ID uniqueness checker now runs in tests and CI. CI triggers now cover every governed standards module, ECM, ADRs, templates, and root governance documents, and the workflow uses the Engineering Assessment Platform identity.

Markdown, HTML, ECM admitted-score views, the platform specification, and the operator guide state the same boundary. This slice preserved schema v4 pending the separately recorded v5 resolved-item migration above; historical packages are not reinterpreted.

Grant Readiness now renders successful decisional evidence as `Overall: READY` in both Markdown and HTML, missing admitted evidence as `NOT EVALUATED` rather than a failed gate, and correctly states that exact repeats cannot repair distinct-scenario breadth. Corpus health distinguishes calibration-metadata completeness, human design review, and empirical calibration rather than blending them. Repository-audit text detection is exhaustive, deterministic, and cached, eliminating the large-YAML-corpus false negative that hid the repository's real pytest CI gate.

Evidence Package schema v4 records the sample-adequacy policy so legacy runs retain their original interpretation. Automated review batches up to eight response/task pairs per judge request, bounds batches by the declared context window, recursively splits malformed batches, preserves successful ratings across partial judge failures, and still validates and persists one rating per response.
- **Legacy rubric-coverage migration completed** ([ADR-0007](adr/ADR-0007-Scenario-Rubric-Applicability-Metadata.md)): reviewed all 124 legacy scenario warnings and added competency- and task-family-specific anchors for every previously uncovered EV dimension. No warning was suppressed and no dimension was bulk-declared non-applicable. `aies suites validate` now reports zero warnings and zero errors; the per-scenario disposition is recorded in [RUBRIC_COVERAGE_MIGRATION.md](platform/RUBRIC_COVERAGE_MIGRATION.md).

Uncalibrated automated reviewer ratings remain traceable but are excluded from qualification scoring, competency levels, grant readiness, and autonomy claims. `aies qualify --decisional` verifies sufficient distinct-scenario breadth for every selected area, while ordinary runs warn before collecting a known non-decisional sample. ECM labels observation coverage rather than calling it confidence.

- **Canonical human-readable identifier convention** ([ADR-0010](adr/ADR-0010-Human-Readable-Identifier-Convention.md)): all reader-facing taxonomy identifiers use `CODE — Title`; raw codes remain only where a machine contract, path, flag, or stable record ID requires them. - **One-command resumed automated evaluation**: `aies qualify --resume <run> --judge <deployment>` now scores (or safely reuses a prior score from) already-collected responses, aggregates, and writes Markdown, HTML, JSON, and ECM artifacts in one invocation. Optional human review declarations can travel in the same command; no separate `review` or `resume` handoff is required for routine evaluation.

CLI completion output lists each generated path.

- **Human review without a grant**: `aies review` now accepts `--consider-advisory-review` and `--human-evaluation NAME`, persists that declaration in the review package, and renders it in the evidence report. This lets a human record consideration of automated advisory evidence and a qualitative or scored human evaluation on non-decisional runs; it deliberately does not bypass grant readiness.

- **Human evidence-consideration record**: `aies grant` can now record whether the authority considered available advisory model-review evidence (`--consider-advisory-review`) and name the evaluator whose qualitative or scored human review was considered (`--human-evaluation NAME`). The durable Qualification Report renders both declarations as separate, human-accountable evidence sources; neither flag changes scores, gates, competency levels, or grant authority.

- **Actionable model-review handoff**: `aies review <run> --model-reviewer <deployment>` now aggregates and refreshes Markdown, HTML, JSON, and ECM artifacts after scoring, rather than leaving recorded reviewer scores stranded behind a separate resume step. Evidence reports show **Automated review** beside **Human review (optional)** for each EV dimension. Uncalibrated reviewers remain visibly advisory for peer-review admission and can never record a grant; their structured scores are still retained as automated evidence. Re-running the same reviewer safely reuses already-recorded ratings instead of duplicating calls or violating append-only rating provenance.

- **Subject-neutral evidence identity** ([ADR-0009](adr/ADR-0009-Engineering-Assessment-Platform-Identity.md)): new runs and Evidence Packages carry a canonical `subject` envelope (`id`, `kind`, display name, executor kind). Current `model` fields remain as compatibility evidence for the existing AI-deployment executor. This preserves existing qualification and comparison workflows while allowing future agents, MCP servers, RAG systems, pipelines, and platforms to use the same canonical evidence architecture.

- **Evidence-package Capability Summary**: Markdown and HTML Qualification Evidence Packages now include a clear informational link to their Engineering Capability Matrix companion. Every `report.write_reports` invocation writes the companion Markdown, JSON, and HTML artifacts beside the run, preserving the audience boundary: evidence package for governance, ECM for engineering use.

- **Reviewed rubric-applicability validation** ([ADR-0007](adr/ADR-0007-Scenario-Rubric-Applicability-Metadata.md), [SCENARIOS.md](platform/SCENARIOS.md)): an uncovered EV dimension may be declared `not_applicable` only with a task-specific rationale. `aies suites validate` rejects malformed, empty, unknown, or contradictory declarations; it separately reports valid declarations and continues to warn on every undeclared omission. The original 124-warning migration queue is now fully resolved by explicit anchors and documented in the migration ledger.

- **Accepted rubric-applicability metadata** ([ADR-0007](adr/ADR-0007-Scenario-Rubric-Applicability-Metadata.md)): defines a narrowly additive, reviewed way to distinguish a deliberately non-applicable EV dimension from an accidental partial rubric. It changes no scoring, gate, autonomy, or grant semantics.

- **Release-hygiene gate** (`make release-hygiene`, CI): checks the tracked release tree and fails if it contains a real `.env`, `.DS_Store`, Python bytecode, `__pycache__`, `.pytest_cache`, egg-info, or `aies-workspace`. Ignored local artifacts may remain in a developer checkout but cannot silently enter a release.

- **Engineering Capability Matrix (ECM)** (`aies capabilities <run-or-deployment> --ecm`): a read-only Markdown, JSON, or self-contained HTML view derived from scored response and rating records. It maps scenarios through the versioned AIES Engineering Task Taxonomy, displays all tasks (including explicit `not assessed` gaps), retains scenario-family evidence and scenario IDs for traceability, and distinguishes observed performance from evidence confidence. Its unweighted EV mean is an inspection statistic only; every output is informational, and non-decisional rows demand more independent evidence rather than making a strength or deployment claim. `--write` saves `engineering-capability-matrix.{md,json,html}` beside the run. See [AIES-ECM-01](ECM/README.md), [ADR-0007](adr/ADR-0007-Scenario-Rubric-Applicability-Metadata.md), and accepted [ADR-0008](adr/ADR-0008-Engineering-Capability-Matrix-Standard-and-Task-Taxonomy.md).

- **Accepted ECM boundary and implementation roadmap** ([ADR-0006](adr/ADR-0006-Engineering-Capability-Matrix-Boundary.md), [OSS maturity TODO](docs/OSS_MATURITY_TODO.md)): separates qualification, the subject-neutral Engineering Capability Matrix, and bounded Deployment Guidance. The future task-mapping registry, confidence rules, protocol-matched comparison, and workload-based selection remain explicitly evidence-derived and non-authoritative; no ECM standard or task taxonomy is adopted by this ADR.

- **Project evaluation and Engineering Capability Matrix direction** ([docs/PROJECT_EVALUATION.md](docs/PROJECT_EVALUATION.md)): records a non-normative assessment of the repository's strengths, adoption blockers, measurement priorities, and delivery recommendations. It defines a staged, subject-neutral Engineering Capability Matrix (ECM): first a read-only, task-oriented renderer over canonical evidence and existing scenario families; only then, subject to ADR and human review, a possible new standard boundary and task taxonomy. The direction preserves the platform's gate-first, non-decisional, human-grant boundaries: task claims must retain scenario, sample, uncertainty, and rater provenance, and never let high averages offset safety or evidence gaps.

- **Independent-engine conformance + a mock empirical demo + coverage expansion** (executing the "next steps" that need no architecture change): (1) **`aies conform engine --engine "<cmd>"`** verifies a **foreign** decision engine against the same golden corpus — the command reads `{evidence, assessment}` JSON on stdin and prints the Canonical Assessment Result on stdout, so an independent implementation self-checks *without importing this package*. A self-contained [`conformance/example_engine.py`](conformance/example_engine.py) (~50 lines of pure Python, **no `aies` import**) reimplements AESQS decision semantics 1.0 from the spec and passes all 8 cases — proof the standard is reproducible independently. (2) **`make demo-empirical`** ([scripts/demo_empirical.py](platform/scripts/demo_empirical.py)) runs the Phase-2 harness on a *synthetic* 3-ability panel so you can see real discrimination output offline (9 scenarios discriminate, 1 deliberately flagged) — clearly labelled synthetic; no scenario is promoted. (3) **Coverage expansion driven by the tool's own findings**: `corpus health` flagged that the RT3 `security` assessment's CA-01 sat one scenario short of the depth target, so CA-01 gained a genuine new high-tier behavioral kind — **multi-agent compositional autonomy** (`SC-CA01-020`: tiering a chained pipeline on its *composed* blast radius, not per-agent) — which closes the gap (health now reports no thin mandatory areas). The remaining advisory diversity gaps were deliberately **not** force-filled, to avoid Goodharting the corpus-health metric.

- **`aies corpus health` — the platform reviews its own assessment corpus** (continuous QA for the assessment system; "AIES measures the quality of AIES"). It reports four **independent, evidence-backed dimensions** — *calibration* (199/199 design-time calibrated), *coverage* (RT distribution per area + per-assessment tier depth), *behavioral diversity* (distinct high-tier decision kinds per area), and *empirical maturity* (0/199 until a panel runs) — plus a **ranked, advisory recommendation list** where every item cites its evidence (e.g. "deepen distinct RT3+ scenarios in CA-01 for 'security' — 7 distinct at/above RT3, target 8"). **Deliberately no single aggregate grade**: a lone score would hide the multidimensional truth (an area can be fully calibrated yet behaviorally narrow) and invite Goodhart optimization — a test locks the no-grade invariant. Like every reviewer in AIES it is *advisory* (never a gate, exit 0) and *versioned* (a `methodology_version`, because changing what counts as "thin" changes a recommendation), and it only critiques — it never edits the corpus or approves anything; a human reads the evidence and decides. `aies corpus coverage` shows just the coverage dimension; **`aies corpus duplicates`** is a deterministic, **twin-aware** near-duplicate detector (3-word-shingle Jaccard on prompts + word-set overlap on ceiling anchors) that flags non-twin redundancy candidates for human review — and hold-out twins that are *too* similar on the surface (which would defeat their anti-gaming purpose); the duplication signal is also folded in as a health dimension. On the shipped corpus it flags **0** redundancy candidates — the scenarios are well-differentiated and the twins are surface-distinct. **`aies corpus review <scenario>`** reviews one scenario *as a measurement instrument*: a deterministic **structural** layer always runs (ceiling/floor/gaming/twin-resolvable/empirical-honesty checks against the calibration methodology), and an **opt-in semantic** layer (`--reviewer <deployment>`) asks a model to *critique* the scenario against the design-time criteria — prompted to find weaknesses and explicitly **not to rewrite, approve, or score** it (the reviewer-not-editor principle; the mock adapter emits a synthetic critique so it runs offline). The review carries **no single grade** either — just structural findings + listed concerns. It is the assessment-corpus analogue of `aies audit` (which reviews a *repository's* practice), and the first of a "continuous QA for the assessment system" surface — all advisory, versioned, and human-in-the-loop.

- **Empirical-calibration harness (Phase 2) + a comprehensive demo**: the analysis core for the one calibration step that needs a real-model panel — `aies suites empirical panel.json` computes, per scenario, **discrimination** (do stronger models score higher, monotonically?), **ceiling reach / live floor**, **repeatability** (score stability across repeats), and **twin robustness** (a large hold-out-twin gap flags gaming), then partitions scenarios into *empirically-calibratable* vs *flagged* (`low-discrimination`, `too-easy`, `ceiling-unreached`, `noisy`, `gameable`). It is pure over its inputs (testable without models) and, like a grant, produces evidence + a verdict — a human records the `empirical_status` promotion; the tool never sets it silently (everything stays honestly `empirically_calibrated: false` until a panel runs). The pilot is **one command**: run each panel model through the scenarios, then `aies suites empirical --runs run-strong=3 run-mid=2 run-weak=1` **auto-assembles** the panel from the scored runs (each rating contributes its mean EV score as an observation; hold-out twins come from the calibration metadata) — no hand-written panel file. **Empirical findings are reproducible too**: every result carries an immutable `metadata` block — the panel id (`--panel-id`), the participating models (ability + `run_id` + checksum), the **methodology version** and the **thresholds version *and their exact values*** — because a threshold or panel change can flip a verdict, exactly like a decision-semantics change. A **pre-registered [empirical-calibration study template](research/empirical-calibration-study-template.md)** (under `research/`) turns the first model panel into a publishable study: its Method — panel composition, selection rationale, methodology + thresholds versions/values, scenario set — is fixed *before* running (mirroring [AESQS-CS-01-R12](AESQS/capability-scoring.md) anti-cherry-picking), and it reports observed discrimination, repeatability, limitations, and the scenarios requiring revision. [CALIBRATION.md](platform/CALIBRATION.md) documents the harness and the panel-results format. New **`make demo-full`** ([scripts/demo-full.sh](platform/scripts/demo-full.sh)) is a narrated, fully-offline tour of the *whole* platform — the three subjects it assesses (a model deployment via `qualify`, a repository via `audit`, the standard itself via `conform engine`), the calibrated instruments, a complete automated Engineering Evaluation, the formal qualification/grant boundary, and the Phase-2 harness — and runs in CI.

- **Conformance-claim mechanism** ([docs/CONFORMANCE.md](docs/CONFORMANCE.md), AIES-DOC-08; `aies conform`): defines what it means to conform to AIES — two classes (implementation / adopter), three assurance levels (self-asserted / evidence-backed / independently-reviewed), and a versioned conformance statement — and makes it checkable. `aies conform template` scaffolds a statement, `aies conform requirements` lists the normative requirements the reference implementation enforces (with where), and `aies conform check` validates a statement and verifies evidence-backed claims against live Qualification Records (exiting non-zero, for CI, when an evidence-backed statement is not substantiated). Honest by design: the checker verifies statement structure and record existence/status — not the truth of a qualification or a reviewer's independence. This is what turns AIES from a framework into a standard others can conform to.
- **Standards crosswalk** ([docs/CROSSWALK.md](docs/CROSSWALK.md), AIES-DOC-07): maps AIES's autonomy levels (AL0–AL4) and risk tiers (RT1–RT4) to the CSA *Levels of Autonomy for Agentic AI*, the ASDLC/AI-SDLC autonomy scale, and the EU AI Act; maps AIES modules/artifacts to NIST AI RMF functions and ISO/IEC 42001; and positions AEBOK/AECT relative to ARTiBA AMDEX and CertNexus CAIP. Reframes AIES as the executable qualification layer that plugs into existing governance frameworks rather than competing with them, and states the gap AIES uniquely fills. Mappings are explicitly approximate, one-directional aids — not conformance or endorsement. Linked from the FAQ and the Taxonomy.
- **Discoverable CLI help**: bare `aies` (and `aies help`) now prints the full command map grouped by stage (setup & discovery / qualification / decision & audit / reference), a copy-pasteable end-to-end workflow, **and a full command tree** — every command *and* subcommand (e.g. `profile list`, `qualification history`, `conform check/template/requirements`) with its usage line, introspected from the live parser so it never drifts — instead of erroring; `aies <command> --help` details each command. The usage line is decluttered (a `<command>` placeholder rather than the full brace list).
- **Multi-phase journeys** (`aies journey list/show`, `aies qualify --journey <id>`): a new scenario type that carries one piece of work *through* the SDLC — each step's response is threaded into the next step's prompt — testing lifecycle depth, not just breadth. Steps are recorded as ordinary response records tagged with their competency area, so the entire existing pipeline (score → aggregate → report → grant → verify) consumes journeys unchanged. Ships JOURNEY-01 (requirement → architecture → implementation → tests → release/oversight) and JOURNEY-02 (incident diagnosis → fix → regression test → post-incident governance), plus JOURNEYS.md (AIES-PLAT-05). A single journey is depth not volume, so it renders NON-DECISIONAL on its own by design.
- **Qualification reports** (`aies report QUAL-… [--format md|json|html] [--write]`, `aies report list`): durable, auditor-facing report artifacts rendered from a Qualification Record — the human decision, scoped grant (per-area CL + RT×AL envelope), accountable humans, conditions, status, and the environment it was earned against — written to a listable `reports/` area separate from run directories. Self-contained HTML (no external requests). `aies report <run>` (evidence-package report) is unchanged.
- **Model-reviewer execution** (`aies review --model-reviewer <deployment>`): the platform now drives a reviewer deployment to critique and score each candidate response (structured EV1–EV6 output, parsed best-effort — an item that can't be parsed into six 0–4 integers is skipped and reported, never fabricated), ingests the results as `model`-kind ratings, and applies the calibration gate. Completes the M4 peer-review loop as an execution framework rather than a hand-authored scoresheet.
- **`aies runtime` resource command + RUNTIMES.md** (AIES-PLAT-04): runtime is now a first-class resource — `aies runtime list` shows every adapter, its contract version, and availability; `aies runtime inspect <id>` shows capabilities, the endpoint env var + conventional default, and models served now. RUNTIMES.md documents the frozen v1.0 runtime interface, the six shipped adapters, and how to add one out-of-tree.
- **Resource-model CLI + qualification manifests**: noun-verb commands `aies deployment` (list/inspect/add/retire), `aies profile` (list/show/validate), and `aies qualification` (list/show/history/verify/revoke) as the primary surface, alongside the existing verbs. Qualification records now carry human-friendly sequential ids `QUAL-YYYY-NNN` and are enriched into a self-contained audit manifest (deployment, model, runtime, checksum, scope, evidence, environment fingerprint, humans, status). New platform docs: `PROFILES.md` (AIES-PLAT-02) and `DEPLOYMENTS.md` (AIES-PLAT-03, "qualify deployments, not models"). Fix: the `architect` profile weighted CA-03 (Product & Experience) instead of CA-04 (Architecture & Solution Design) — a stale weight from before ADR-0003.
- **Built-in adapters for common local runtimes** — `ollama`, `lmstudio`, `llamacpp`, and `mlx` (thin subclasses over the OpenAI-compatible HTTP adapter), each auto-detected on its conventional port and overridable via its own `AIES_<RUNTIME>_BASE_URL`. `aies doctor` reports all runtimes; `aies discover` registers whatever each serves. Configurable probe timeout (`AIES_PROBE_TIMEOUT_S`). The platform GUIDE gains per-runtime setup and a start-to-finish worked run.
- **Platform configuration via env vars / `.env`** (`config.py`, `.env.example`): all operational settings — workspace path, `openai-compat` endpoint and API key, request timeout, parallelism, and generation defaults (temperature/max-tokens/top-p/seed) — are read from the environment or a git-ignored `.env` file, with a dependency-free loader (precedence: CLI/manifest → real env → `.env` → default). The hard-coded `localhost:11434` endpoint default was removed (unset now means "runtime not configured"). Normative engine constants (gates, weights, sample minimums, confidence, calibration threshold) remain deliberately non-configurable (D3), with a test enforcing it.
- **Platform Milestone 4 — review & workflow** (completes the platform): multi-model peer-review orchestration (`aies review`) with the reviewer-model **calibration gate** (an unqualified, uncalibrated reviewer's scores are advisory only) and divergence surfacing (≥2-point or gate-changing disagreements are listed for human resolution, never averaged); the **human grant workflow** (`aies grant`) producing a **Qualification Record** — a named human authority records every decision, a second human is required to grant, and grants on non-decisional or gate-failing evidence are refused (the platform never grants); the **status model** (active/conditional/denied/invalidated/revoked/superseded) with `aies verify` enforcing the **environment-change re-qualification trigger** (D7 — a changed fingerprint invalidates a grant, non-zero exit for CI); `aies qualifications` (list/show/revoke); an HTML `aies dashboard`; and a GitHub Actions CI workflow running the conformance suite on Python 3.10–3.12. Platform milestones M1–M4 complete.

### Added

- **`aies deployment update` / `aies deployment remove`**: fixing a registered deployment no longer means hand-editing a workspace file or juggling ids. `update <file>` overwrites an existing entry in place (same id) — for a wrong endpoint, an `api_key_env` typo, changed generation defaults, or adding `roles: [judge]` — and **warns** when a behavioral-identity field (runtime, model, quantization, `runtime_config`) changed, since prior qualifications for that id may no longer describe what runs (the D7 fingerprint catches it on `verify`). `remove <id>` hard-deletes an entry so its id is free to reuse, as a counterpart to `retire` (which soft-marks and keeps the id reserved for audit). `add` remains new-ids-only. Surfaced by first-real-run friction (fixing a mis-registered judge required deleting the stored YAML by hand).

- **Troubleshooting guide ([platform/TROUBLESHOOTING.md](platform/TROUBLESHOOTING.md), AIES-PLAT-06)**: symptom → cause → fix for the issues that actually come up against real endpoints — timeouts, `CERTIFICATE_VERIFY_FAILED`, `401/403/404/429`, slow runs (`max_tokens`/`--repeats`), `--parallel` on local GPUs, re-scoring a collected run after a judge failure, `already registered` (use `update`), and low judge parse rates. Linked from the platform README, GUIDE §5.2, and the `aies help` epilog. GUIDE also gained the re-score-without-recollect flow and a performance note.

### Fixed

- **`python -m aies` now propagates the CLI exit code.** `__main__.py` called `main()` without `sys.exit()`, so the module entry point always exited 0 — meaning a shell/CI check like `python -m aies audit .. --gate --rt 3` (or any `--gate`) silently "passed" even when the gate failed. The installed `aies` console script was unaffected (setuptools wraps it), but `python -m aies` gating was broken. Now fixed and covered by a subprocess regression test.

- **HTTPS to cloud judges/endpoints now verifies certificates reliably.** On a freshly-installed Python (notably python.org macOS builds) an HTTPS call failed with `CERTIFICATE_VERIFY_FAILED — unable to get local issuer certificate`. The `openai-compat` adapter now builds its TLS context from **certifi's** CA bundle (added as a dependency), while still honoring an explicit `SSL_CERT_FILE`/`SSL_CERT_DIR` (corporate CA). TLS-verification failures also get a specific remediation hint instead of being lumped in with timeouts, and timeouts no longer misreport a fast failure as "within 300s". `aies review --model-reviewer` gained `--parallel` (and a worker banner), so re-scoring an already-collected run with a judge is concurrent — you can re-run just the judge step against saved responses instead of re-collecting.
- **Endpoint failures are now actionable, and never lose collected work.** A request timeout previously surfaced as a bare `error: timed out` with no indication of which endpoint or why (a raw `TimeoutError` slipped past the adapter's `URLError`-only handler on Python 3.14). The `openai-compat` adapter now names the endpoint and the timeout, distinguishes HTTP status errors (401/404/429 with guidance) from unreachable hosts, and suggests `AIES_REQUEST_TIMEOUT_S` / lowering `--parallel`. The pre-run **liveness (smoke) probe** now fails fast (≤30 s) instead of hanging for the full 300 s request timeout when an endpoint is dead or misconfigured. And `execute_suite` now **writes each response as it completes** and raises a single summary error on failure — so a timeout partway through no longer discards the responses already collected (previously a parallel batch was all-or-nothing). Surfaced by first-real-run feedback (`collecting responses across 8 worker(s).. error: timed out`).
